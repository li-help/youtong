## 第一幕 · 开场（P1–P2，约 45 秒）

### P1 封面（30s）
各位老师好。今天我汇报的项目叫「优童成长社」，一个面向 0 到 6 岁儿童家庭的母婴服务平台。它一共四个端——家长的 App、微信小程序、H5，加上运营用的管理后台，背后是一套 Spring Boot 服务，接入了 DeepSeek 大模型。特别说明一点：它不是 PPT 项目，**已经真实部署在云服务器上运行**。下面我从"为什么做、怎么做、遇到了什么问题"三个层面来汇报。

### P2 目录（15s）【指图】
整个汇报分五个部分，对应五个问题：为什么做、怎么设计、怎么实现、遇到什么问题怎么解决、效果如何。其中分量最重的是第三部分的四个核心功能和第四部分的四个技术难点。

## 第二幕 · 项目与需求（P3–P7，约 2 分 15 秒）

### P3 分节页（5s）【快翻】
第一部分，项目与需求——先回答"为什么值得做"。

### P4 背景痛点（35s）
先说为什么做。家长这边：早教课程五花八门越查越乱，亲子活动不知道哪里有，看中了还要电话咨询、线下跑腿；运营这边：内容和订单靠表格和微信群管，改一张宣传图都要等开发排期。【停顿】两边其实是同一个矛盾——**服务数字化程度太低**。所以目标就一句话：家长在一个平台完成"发现、咨询、下单、参与"的全流程；运营在后台点几下鼠标完成全部管理。

### P5 场景与用户（30s）【指四张场景卡】
目标用户两类。家长是 0 到 6 岁宝宝的父母，时间碎片化、手机优先；运营是非技术背景的运营和客服，诉求是不写代码完成全部工作。下面这条时间线是真实跑起来的场景：周一晚上问 AI 育儿问题，周三下单课程拿到核销二维码，周六到店扫码核销——而这期间运营上架的任何新课，家长端都会自动刷新。这就是产品的日常运转方式。

### P6 功能概览（30s）【指底部数字条】
需求落到系统上，就是家长端五大板块、运营端十二个模块。请记住底部这组数字：三端加后台一共六十多个页面，后端**一百零八个接口、十七张表**——后面讲的所有功能都有这个规模兜底，不是概念稿。

### P7 业务流程（40s）【指三条泳道，逐条指】
把需求串起来是三条主线。第一条家长侧：发现内容、AI 咨询、必要时转人工、收藏下单；第二条交易闭环：下单支付、生成二维码、到场核销、全程可查；第三条运营侧：后台管理、版本号变更、推送同步、家长端自动刷新。三条线跑在同一个账号体系和同一个数据库上——这就是"一个平台"的含义。

## 第三幕 · 系统设计（P8–P14，约 3 分 20 秒）

### P8 分节页（5s）【快翻】
第二部分，系统设计。

### P9 总体架构（45s）【指架构图自上而下】
这是整体架构。最上层四个端，共用同一套 REST API 和同一个数据库——功能开发一次，四端同时可用。中间 Nginx 是统一入口，除了反代 API，还托管 WebSocket 长连接、SSE 流和静态资源。往下是 Spring Boot 标准三层：二十个 Controller、二十个 Service、十七个 Mapper。再往下是 MySQL 十七张表加本地文件存储，最下面三个外部服务：DeepSeek、阿里云短信、微信开放能力。【指三条彩色通道】特别注意这三条通道：REST 管请求响应，WebSocket 管客服实时消息，SSE 管内容变更推送——后台改了内容，家长端自动刷新，不用发版。

### P10 三条通道（30s）
展开说为什么是三种。REST 覆盖所有请求响应式的业务；双向实时只有 WebSocket 能做；而内容同步只是单向广播，用 SSE 更轻、浏览器自带重连，小程序和 App 不支持 SSE，就退到五秒轮询版本号兜底。三者是分工，不是堆砌。

### P11 技术栈（25s）【快讲，六张卡扫一遍】
技术栈一句话概括：一套代码出两端——Flutter 出 Android 和 Web，uni-app 出小程序和 H5，四个客户端其实只有两份前端代码；后端 Spring Boot 3 一个技术栈扛起三种通信；AI 用 OpenAI 兼容协议直调，换模型只改配置。

### P12 关键选型（40s）【指第 3、4 行】
这一页每个选型都写了理由和代价，我重点说两个。第一，MyBatis-Plus 而不是 JPA，因为管理后台全是密集增删改查，通用 CRUD 加分页插件正合适。第二，最容易被追问的——**为什么没有 Redis？**【停顿】因为当前是单机部署，验证码这类数据生命周期只有五分钟，内存方案够用；而且我把它们全部收敛在独立的类里，换 Redis 不用动上层。代价我也写在右边：重启丢状态、无法水平扩展，已列入规划。

### P13 数据库总览（25s）【指四个分组】
数据库十七张表分四个域：账号四张、内容八张、交易一张、客服与智能四张。底部是贯穿全部表的设计约定：InnoDB、逻辑外键加索引、幂等唯一键、金额一律 DECIMAL。

### P14 ER 与 IM 链路（40s）【指中间 ER，再指底部状态机】
重点讲 IM 这条链路。会话表用"用户 ID 加门店 ID"拼成复合唯一键，保证一个用户对一个门店只有一个会话，AI 和人工共享上下文——**这是后面转人工能无缝的根本原因**。消息表的客户端消息号唯一键做幂等，断线重发也不会重复落库。未读数做了用户、客服双计数，属于反范式，用冗余换掉高频 count 查询。底部是会话状态机：AI 接待、转人工、结束切回 AI，全程同一个会话。

## 第四幕 · 核心实现（P15–P23，约 4 分 40 秒）★ 全场重心

### P15 分节页（5s）【快翻】
第三部分，核心实现，今天分量最重的部分。

### P16 功能① AI 育儿问答（40s）【指三级漏斗，逐级指】
第一个功能，AI 育儿问答，链路是三级漏斗。第一级正则识别转人工类意图，命中直接转接；第二级查 FAQ 知识库，二十二条知识按七类组织、关键词分词匹配，命中就**毫秒级返回，完全不花大模型的钱**；第三级才是 DeepSeek，带最近六轮历史生成两百字以内的回答。每一级都有降级出口——大模型挂了就返回固定话术引导转人工，主流程永远不会报错。

### P17 功能② 实时客服 IM（40s）【指左链路，再指右协议】
第二个功能，实时客服。左边链路：家长端无论 uniapp 还是 Flutter 走同一个 WebSocket 协议，经 Nginx 升级连到后端，消息先落库再路由到客服工作台。右边六个消息类型里，ACK 回执和 ping 心跳是可靠性的基础；未读数做了两层设计；工作台还配了 FAQ 快捷回复和提示音。会话结束客服可以关闭，用户切回 AI 接待，并打一到五分评价。

### P18 功能③ 订单闭环（30s）【指状态机】
第三个功能，交易闭环，核心是状态机：待支付、已支付、已核销，外加取消。四个要点：唯一订单号做幂等；金额用 DECIMAL 防浮点误差；核销接口校验状态必须是已支付，非法流转直接拒绝；三个时间戳全程可追溯。微信支付的真实回调将来就挂在"已支付"这次状态变更上，挂载点已经留好。

### P19 功能④ 推荐 + 同步（30s）【左右各指一遍】
第四个功能是特色入口"小宇宙计划"：家长填宝宝年龄和兴趣，系统从真实业务数据检索候选——四门课、三个活动、三个视频——再让大模型写百字推荐语，不可用就用模板兜底。右边这套同步机制是运营的命脉：后台每次保存，基类自动推高频道版本号，H5 走 SSE、其他端五秒轮询，家长端自动刷新——**运营改任何内容都不需要发版**。

### P20 前端三端同构（30s）【指底部四个约定】
前端最有价值的是"同构复用"。三端遵循完全一致的契约：统一响应信封、统一 token 注入、统一 401 处理、同一套 WebSocket 协议——所以 Flutter 端和 uniapp 端的 IM 服务是逐行对应的两个实现，谁也不会悄悄漂移。

### P21 跨端复用（35s）【指两张对称卡】
双框架策略为什么成立？因为前后端各有一个"配置驱动"的抽象，而且是对称的：后端 CrudController 基类让十二个模块声明实体就自动拥有四个接口；前端 ListPage 组件让十二个列表页只传三个配置就完整生成。新增一个管理模块，两端的工作量都收敛到"填配置"。下面这条是 AI 客服页的生命周期，在两端逐行对应。

### P22 后端分层（30s）【指右侧五步】
后端是标准三层，控制复杂度靠两个设计：一是 CrudController 把十二个模块的增删改查全部下沉；二是统一协议——所有接口同一个信封、所有异常被全局处理器兜住、认证集中在拦截器加白名单。右边是 AI 客服接口的完整五步链路，每一步的出口都明确。

### P23 API 案例（40s）【指代码块】
把案例拆到底。上面五步链路注意三个分支：命中转人工意图立即短路；命中 FAQ 直接返回，顺便给知识热度加一；第五步任何异常都降级成固定话术。下面是订单核销的真实校验代码：状态不是"已支付"就直接拒绝。【停顿】这两个案例说明一件事——接口层的可靠性来自"**每一步都有明确出口**"这个纪律。

## 第五幕 · 攻坚与加固（P24–P30，约 3 分 45 秒）★ 情绪高点在 P28

### P24 分节页（5s）【快翻】
第四部分，四个真实踩过的坑。

### P25 难点① AI 可用性（40s）
难点一：大模型又慢又贵还不稳定，直接当客服不可用。方案是三级漏斗加六十秒超时熔断。原理上是检索增强思想的最小实现——**能检索到的绝不生成**。效果是高频问题变成一次数据库查询、毫秒级返回，答案口径由运营维护、完全可控。这些是定性结论，我没有编造量化指标。

### P26 难点② 消息可靠性（40s）【指右侧时序】
难点二：手机切网、锁屏都会断连，重发会重复、不重发会丢。我的方案是一套应用层确认协议：每条消息带客户端生成的消息号，先进待确认队列；服务端落库前按数据库唯一键查重，成功才回 ACK；六秒没收到就标记失败、允许重发——重发也不怕，唯一键挡着；断线四秒自动重连，重连后拉历史补缺口。最终做到消息**不丢、不重、状态可恢复**。

### P27 难点③ 无缝转接（35s）【指右侧三级调度】
难点三是转人工。转接前会话没有客服归属，而且目标客服可能不在线。方案三步：先三级调度选人——本店在线优先、本店其次、全平台兜底；选中后把会话从 AI 切到人工、写入客服 ID；再发系统消息并通过 WebSocket 同时通知两端。关键是全程同一个会话 ID，用户之前跟 AI 说的话客服全看得到，体验上是无缝的。

### P28 难点④ 清库事故（50s）【放慢语速，这是真实故事】
难点四是一次真实事故。【停顿】我们的 schema 文件里带 DROP TABLE，早期部署直接导入，等于每次发版都可能把线上库清空——**这真实发生过**。修复分两层：脚本层，把初始化改成幂等的——检测到库里已有数据，自动把 schema 转换成安全版，DROP 整行剔除、CREATE 改成 IF NOT EXISTS，只补缺失的表和列；校验层，部署后核对表数量和十四张核心表，再做六十秒健康检查，加上十份备份随时回滚。【停顿】修复之后到现在，自动部署零数据事故。这件事的教训是：**自动化流程里的每一个假设，都必须有校验兜底**。

### P29 安全（25s）
安全做了六层：JWT 认证、BCrypt 存密码、方法级白名单、SQL 全预编译、上传类型白名单加 UUID 重命名、密钥全走环境变量、仓库零明文。同时如实说三个没做的：HTTPS、token 刷新、按钮级权限——都列入了最后的规划，不回避。

### P30 性能（25s）
性能先声明：目前没有系统性压测数据，所以只讲机制、不编数字。收益最大的是 AI 链路——FAQ 挡在大模型前面，高频问题毫秒级返回还省了调用；数据库侧高频查询全有索引、全接口强制分页；网络侧静态资源交给 Nginx，同步用版本号做增量感知。答辩后我会用 JMeter 补一组对比数据替换这个占位框。

## 第六幕 · 上线与收获（P31–P34，约 2 分钟）

### P31 分节页（5s）【快翻】
最后一部分，上线与收获。

### P32 部署（40s）【指流水线六步】
推一次代码，GitHub Actions 并行构建四个产物：后端 jar、后台前端、安卓安装包、Flutter Web，自动上传服务器——上传前备份旧版本，保留十份随时回滚；数据库初始化幂等，绝不覆盖线上数据，这就是清库事故换来的防线；重启后两道验收：健康检查加表结构校验，任何一道不过就判失败。运行期 systemd 守护，宕机五秒自动拉起。整套流程十几分钟，**无人值守**。

### P33 成果（30s）【指六个数字】
成果全部可以在代码里核实：四端、一百零八个接口、十七张表、六十多个页面。比数字更重要的是三件事：第一，它真跑在生产环境；第二，三端共享一套 API，新端接入成本趋近于零；第三，AI 不是展示品，三条链路都长在真实业务数据上。

### P34 总结（40s）
总结：这个项目完成了母婴服务从内容、咨询、交易到客服的全流程数字化，并且真实上线。技术上完整实践了三种前端，加 Spring Boot、WebSocket、AI 接入、CI/CD 的全链路；更重要的是工程方法上的收获：统一协议、幂等设计、降级兜底、防事故部署。规划不空谈，每条都对着真实短板：用 Redis 解决单机内存态、用 HTTPS 和真实支付补全交易合规、补自动化测试、把 FAQ 升级成向量检索。我的汇报到此，谢谢各位老师。【停顿，点头致意，进入问答】
